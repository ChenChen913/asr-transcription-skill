## 1. 它是什么

一句话：**把视频里某几个时间点的真实画面截下来，紧凑拼成长图**，字幕靠画面自带的像素（原生字幕模式）或后期绘制（脚本字幕模式）。

| 项 | 值 |
|---|---|
| 版本 / 提交 | v2.11.0 / `02bb01d`（2026-11-06） |
| 许可证 | MIT，Copyright (c) 2026 程意 |
| 文件数 | 76（不含 `.git`） |
| 核心脚本 | `skills/native-subtitle-quote-image/scripts/native_subtitle_stitch.py`，**1508 行 / 64 KB** |
| 依赖 | **只有两个**：`imageio-ffmpeg>=0.5`、`Pillow>=10.0` |
| 测试 | 6 个文件、**147 个用例、370 条 assert**，`unittest`，无网络无模型 |
| CLI | 5 个子命令：`check-source` / `sample` / `band` / `render` / `render-script` |
| 三语 README | 中 / 英 / 韩；案例图与相对链接由 `validate_repo.py` 约束（不含正文一致性） |

规模上它比我们大（我们主脚本 4 个、测试 3 套 1028 断言），但**依赖策略比我们更极端**：连 numpy 都不用，纯 Pillow 做图像判断。这一点值得单独记住——它证明了「不引 numpy 也能做像素级判断」。

### 1.1 它明确不做什么

这几条写在 `CLAUDE.md` 的「不可违背的原则」里，不是随口说说：

- 原生字幕模式**只裁切**画面里已有的字幕，不 OCR、不重绘、不翻译、不覆盖。
- 脚本字幕模式必须标注为「后期绘制」，不得冒充原字幕。
- 不帮助绕过 DRM 或平台访问控制。

所以它和我们的关系不是竞争，而是**上游/下游**（见 §5）。

## 2. 你问的「它是怎么识别每一帧的」——它其实不识别

这一节是全篇最需要纠正认知的地方。它有三层，只有第三层算「判断」，而且判断的是**几何**，不是**内容**。

### 2.1 第一层：定位靠时间点，不靠画面

它的数据流是这样的：

```mermaid
flowchart LR
    A[文字稿或字幕轨] --> B[人和 Agent 读文字<br/>选句子]
    B --> C[候选时间点]
    C --> D[按时间戳取帧]
    D --> E[几何与重复度检查]
    E --> F[拼图]
```

`SKILL.md` 写得很直白：

> 主图（每张图的第一个时间点）由你来选，渲染器不识别人脸、也不自动挑帧，manifest 或 `lines` JSON 写的是哪个时间点就用哪一帧。

`troubleshooting.md` 里对应有一条：主图选错了人怎么办——答案是「换时间点，重新渲染」，而不是「让程序挑」。

**这是它的设计选择，不是能力缺陷。** 它把「选哪一帧」交给能读文字稿的 Agent，代码只管「取这一帧、排好版」。这个分工很干净，但它意味着：**如果你没有时间点，它一步也走不了。**

### 2.2 第二层：取帧——两段 seek

```python
def grab_frame(path, seconds, tmp_dir=None):
    """先快速跳转，再精确解码 3 秒，避免长 GOP 视频错帧。"""
    preseek = max(0.0, seconds - 3.0)
    offset = seconds - preseek
    # ffmpeg -ss <preseek> -i <video> -ss <offset> -frames:v 1 out.png
```

两段 seek 是十几年前 ffmpeg 的经典写法：先在容器索引上跳到目标前 3 秒（快，不解码），再在解码流上做一次输出侧 seek（精确，丢掉 3 秒）。

**实测结果（H.264，GOP=250，25 fps，20 s，画面烧了帧号）：**

| 时间点 | 单段输入 seek vs 精确基准 | 两段 seek vs 精确基准 |
|---|---|---|
| 5.0 s | 逐像素 0 差异 | 逐像素 0 差异 |
| 12.4 s | 逐像素 0 差异 | 逐像素 0 差异 |
| 18.6 s | 逐像素 0 差异 | 逐像素 0 差异 |

耗时（8 个时间点）：单段 **72 ms/帧**，两段 **76 ms/帧**，**多花 5%**。

结论分两半：

- **「避免错帧」这个理由在 H.264 上不成立。** 现代 ffmpeg 的输入 seek 本身就是精确 seek（解到关键帧再逐帧前进丢弃），`-noaccurate_seek` 才是那个会错帧的开关。
- **但代价只有 5%，可以照抄。** 它在索引损坏、时间戳有 B 帧重排、或很老的 ffmpeg 上有防御价值。**建议移植，但把注释改成「成本 5%，为索引异常兜底」**，不要把没复现的说法写成事实。

### 2.3 第三层：两个纯 Pillow 启发式

真正做「判断」的只有两个函数，都不认字：

| 函数 | 判断什么 | 输出 |
|---|---|---|
| `changed_ratio(a, b)` | 两张图差多少 | 160 px 灰度缩略图上，亮度差 > 12 的像素占比 |
| `subtitle_extent(band)` | 一条字幕带里，文字在哪几列 | 左右 x 边界，或 `None`（判定没字） |

`subtitle_extent` 是本次评估的主角，§3.1 拆解。

### 2.4 重复帧：三档拦截，不是一档

`ensure_distinct_frames` 分三种情形，报错文案各不一样：

| 情形 | 判定 | 报错点名的对象 |
|---|---|---|
| 所有时间点画面几乎相同 | 第 1 帧 vs 其余全部 < 0.005 | 静态封面 / 画面冻结 |
| **任意两帧**几乎相同 | 两两比对 < 0.005 | 「2.00s 与 3.00s 的画面几乎相同」（点名两个时间点） |
| 相邻字幕条几乎相同 | 只比字幕带 < 0.005 | 同一句字幕重复 / 这一段没字幕 |

第三档很关键：**它们比的是字幕带，不是整帧。** 我实测这个口径差异是 8 倍（§4.2）。它自己在代码里就这么写了，只是没解释为什么——推测是因为整帧比对看不出「同一画面但字幕换了」。

报错文案统一带三件套：**原因 + 怎么查（去跑 `sample`）+ 逃生舱（加 `--allow-duplicate-frames`）**。这个文风值得抄（§3.6）。

### 3.1 字幕区域检测：本次最值得搬的东西

#### 它原来的算法

`subtitle_extent(band)` 接收一条**已经由人指定好的**字幕带，回答「文字在这条带的哪几列」。四步：

```python
bright   = 灰度 >= 200                    # 够亮
neutral  = HSV 饱和度 <= 70               # 够不彩色（白字是低饱和）
contrast = 灰度 - MinFilter(5) 后的灰度    # 比周围 5 像素最暗处亮 60 以上 = 笔画边缘
mask     = bright & neutral & contrast    # 三个条件相乘
```

然后 `mask.resize((width, 1), BOX)` 把掩码压成**一列**，每个值就是该列的「文字像素占比」；按阈值切段、按 4% 宽度合并相邻段、丢掉质量不足最强段 25% 的段，剩下就是左右边界。

设计意图写得很清楚：

> 只用于决定两侧能裁多少：宁可把背景误判成文字而少裁，也不能漏掉文字。

**这是「保守优先」的算子，方向正确。**

#### 我的改造：把列投影换成行投影

它只需要左右边界（因为上下边界是人给的）。我们要的正好相反：**上下边界**——那正是 `docs/字幕识别与OCR_调研与设计.md` §6.4 里靠人填 `--band-top 0.78 --band-bottom 0.96` 的地方。同一套掩码，压成一行就是每行的文字像素占比。

我加了三条先验（它没有，也不需要）：

1. **只看下半幅**（`y >= 0.55h`）——烧录字幕几乎总在下半部；
2. **行高合理性**——少于画面高度 0.9% 的簇丢弃（噪点、UI 细线）；
3. **向上合并**——与当前簇间距 ≤ 1.6 倍行高就并入（两行字幕）。

#### 实测结果（1920×1080，`testsrc2` 彩条背景 + 真实中文字幕）

| 样本 | 真值 | 检测结果 |
|---|---|---|
| 单行 f1 | y = 960–1008（0.889–0.933） | **0.890–0.930**，x = 627–1294 |
| 双行 two | 890–938 + 960–1008 | **0.825–0.930**（两行合并成功），x = 724–1196 |
| 无字幕 none | 无 | **None**（正确拒答） |
| 灰底单行 g1 | 同 f1 | **0.884–0.936** |
| 灰底双行 gtwo | 同 two | **0.819–0.935** |

耗时（同一张 1080p 帧）：

| 处理宽度 | 耗时 | 精度 |
|---|---|---|
| 1920 | 110 ms | 基准 |
| 960 | 30.5 ms | 差 0.001 |
| **640** | **14.3 ms** | **差 0.003** |
| 480 | 7.9 ms | 差 0.002 |

**降到 640 宽做检测，14 ms/帧，精度仍在 0.3% 以内。** 按这个成本，逐帧检测也不贵，但没必要——每部片子抽 3–5 帧确认位置稳定即可。

#### 反例：照抄选簇规则会翻车

我第一版按它的逻辑「取最大的簇」，在全灰（低饱和）背景上直接错：

| 样本 | 正确字幕位置 | 取最大簇的结果 |
|---|---|---|
| g1（灰底 + 底部字幕） | 0.884–0.936 | **0.167–0.231**（画面**上方**的亮区，选中 64 行） |
| gtwo | 0.819–0.935 | **0.166–0.231**（同样错） |

原因很简单：它面对的是一条已经切好的窄带，带里除了字没有别的东西；我们面对的是**整帧**，亮而低饱和的区域（白墙、灰幕、白衣、天空）到处都是，而且面积比一行字大得多。

**所以：借掩码，不借选簇规则。** 加上「下半幅 + 行高合理 + 向上合并」之后，同样的灰底样本全部修正为 0.884–0.936 / 0.819–0.935。

#### 必须写进设计的一条警告

检测出字幕带之后，**绝对不要直接把它裁出来当 OCR 输入**。

这是两个项目发现的交集，也是本轮最容易踩的坑：

- 本项目早前实测：把 1920p 画面裸裁成 1920×238 的字幕带喂给 RapidOCR，**43 ms 返回空结果，不报错**。因为 RapidOCR 的检测器按短边缩放，超宽条会被放大成巨大画布，单行窄条直接漏检。
- 正确做法是：**用检测到的带做「定位与判定」，OCR 输入仍然走整帧或缩到 1280 宽的整帧**；带只用来（a）判断这一帧有没有字幕、（b）判断字幕是几行、（c）给裁剪/预览提供坐标。

如果一定要裁，就必须补边到接近正常宽高比（我实测 `crop + pad 到 1920×720` 可识别），但那已经是另一条预处理路径，不要混进主链路。

### 3.2 `changed_ratio`：可借，但阈值必须重新标定

算法本身很干净：

```python
# 缩到 160 px 宽、转灰度、逐像素求差
diff = |a - b|
ratio = (diff > 12 的像素数) / 总像素数
```

`DIFF_LEVEL = 12`（避开有损压缩噪声）、`DUPLICATE_PIXEL_RATIO = 0.005`（0.5%），上限 `0.2`，并在常量旁注了理由：

> 真实访谈相邻句子的整帧差异通常在 5% 以上；静态封面重编码后接近 0。

**我实测这句注释对不上。** 同一背景、只换一行字幕的 5 组相邻帧：

| 对比 | 整帧口径 | 字幕带口径 | 倍数 |
|---|---|---|---|
| f0 vs f1 | 0.0128 | 0.1042 | 8.1× |
| f1 vs f2 | 0.0117 | 0.0990 | 8.5× |
| f2 vs f3 | 0.0092 | 0.0792 | 8.6× |
| f3 vs f4 | 0.0088 | 0.0734 | 8.3× |
| f4 vs f5 | 0.0090 | 0.0745 | 8.3× |

两件事同时成立：

1. **「相邻句子差异在 5% 以上」不成立**——整帧只有 0.9%–1.3%。它能工作是因为阈值取在 0.5%，余量只有 **1.8–2.6 倍**，不是它注释暗示的 10 倍。
2. **换字幕带口径后余量变成 15–21 倍**，安全得多。

对我们的直接结论：

- 用它做「拒绝渲染」：阈值 0.005 **偏紧但可用**，2 倍余量意味着相近的两句（「我们继续」vs「我们接着」）可能被误判成重复。**我们不该照抄 0.005。**
- 用它做「相邻帧去重」（v0.7 的真实需求）：**必须只在字幕带内比，阈值从 0.005 提到 0.05 量级**，并按实测重新标定。方向也要反过来——它怕「漏拦重复」，我们怕「误合两句」。

这条要在 v0.7 落地时用真实素材重新标定，我这轮只有合成样本，不下最终阈值。

### 3.3 两段 seek

见 §2.2。移植，注释改写。

补充一个它做得对的细节：临时文件名用 `tempfile.mkstemp`，并且 `finally` 里 `unlink`。**抽帧不留垃圾**——本项目 `batch_transcribe` 也是同样的洁癖，一致。

### 3.4 `is_valid_image`：和我们 v0.5.1 同一个教训

```python
with Image.open(path) as image:
    image.verify()
# verify() 不解码像素，查不出被截断的 JPEG；再完整解码一次。
with Image.open(path) as image:
    image.load()
```

注释是对的。我实测：把一张 227 KB 的 JPEG 分别截断到 90% / 50% / **10%**：

| 截断比例 | `verify()` | `verify()` + `load()` |
|---|---|---|
| 90% | **通过** | OSError |
| 50% | **通过** | OSError |
| 10% | **通过** | OSError |

**截到只剩 10% 它也说「没问题」。** 这和本项目 v0.5.1 修的「JSON 能解析 ≠ 交付完成」是**同一个错误的两个版本**：校验只看容器外壳，不看内容是否完整。

可移植性：如果将来本项目要产出图片（比如字幕带预览图、质检缩略图），产物校验一律走「两段」，不要只 `verify()`。这条建议现在就可以写进 `qc_check` 的图片分支。

### 3.5 候选帧总览与红线预览

两个小工具，交互价值大于技术价值：

- `sample`：给一批时间点，抽帧拼成带时间码的缩略总览（默认 4 列、320 px 宽、上限 48 帧），人一眼看完整段。带 `-t ... --around 0.8` 时，每个时间点生成**前/中/后三帧**。
- `band`：在指定时间点的画面上，用红线画出 `--band-top/--band-bottom` 两条边界，存成预览图。

`band` 这个设计很聪明：**它不信任自己算出来的边界，让用户在真画面上看一眼。** 它的默认带是 `0.78–0.96`，和本项目上一版手工猜的数字一模一样——说明这个默认值在中文视频里确实常用，但也说明**它一直没有解决「带对不对」这个问题**，只是给了一个预览工具。

如果我们做了 §3.1 的自动检测，等价能力应该是「打印检测到的带 + 生成一张画了框的预览图」，而 `--band-top/--band-bottom` 降级为**覆盖值**（手动指定的优先级最高）。这比「猜 + 让人核对」进一步。

`--around 0.8` 三帧采样的思路也直接可用：v0.6 从字幕轨拿到 cue 起点后，起点往往落在字幕还没完全显示的时刻，取「中段」更稳。它自己的文档里就是这个结论：

> 字幕轨先用来建立「内容—时间点」索引……取字幕完整稳定显示后的中间帧，不取切换瞬间。

### 3.6 `--resume` 与失败报告

本质和我们 `_batch/summary.json` + `is_done()` 是一套东西：状态就是产物本身，失败单独记账。但它有两点比我们细：

1. **跳过时要报数**：`续跑: 跳过 3 张已完成的图`。我们 `batch_transcribe` 也打印 `N already done`，这点已经对齐。
2. **失败报告带 `times`**：`{"index", "title", "times", "reason"}`。我们的 `_batch/summary.json` 记了 `error` 和 `exit_code`，但**没记时间点**——对下游「改完重跑」不够友好，因为修一条字幕需要知道是哪一句。这个可以借。

另有一个默认值差异值得注意：**它默认不覆盖**（`refuse_existing` + `--overwrite`），我们默认覆盖（`--force` 反向开关）。这不是对错，是取舍：它保护「用户好不容易修好的成品」，我们保护「批量重跑不中断」。**不要改我们的默认**，但可以记一笔。

### 3.7 滚动字幕去重：这条规则比代码值钱

这是 `references/yt-dlp-and-transcripts.md` 里的一段，**没有代码，纯规则**，但正好命中 v0.6 会遇到的第一个坑：

> YouTube 自动字幕（含 `en-orig` 等原声轨）是滚动显示的：VTT 里相邻条目常重复上一行文字，同一句话会出现在两三个条目里，条目开始时间也早于该句在画面上完整显示的时刻。直接拿条目开始时间取帧，容易截到上一句或对方的话。

它的处理：

1. 合并文字相同或**前缀包含**的相邻条目，每句只留一条；
2. 开始时间取**首次出现**，结束时间取**最后一次出现**；
3. 用去重后条目的**中段**而不是开始时间作为候选时间点。

**「前缀包含」这个判据比「完全相同」重要得多**：滚动字幕的第二条是第一条加几个字，文本并不相等。只用相等去重会漏掉大部分。

这条要原样写进 v0.6 的 `subtitle_extract.py` 设计——v0.6 的第一件事就是读 SRT/VTT，自动字幕和人工字幕混在一起时，不处理滚动重复，产出的时间轴会整体错位。

### 3.8 不借的部分

| 不借的 | 理由 |
|---|---|
| yt-dlp 下载链（`fetch_source.py` 403/429 退避） | 我们是零网络硬约束，这是红线，不是技术选择。 |
| 三语 README + 案例图 SHA-256 校验 | 我们中英双语已够；`validate_repo.py` 那套「案例图必须登记且哈希一致」对我们的纯代码仓库是过度设计。 |
| 版本检查（`check_update.py` 访问 GitHub） | 同上，零网络。 |
| 排版渲染（拼图、字体、说话人前缀、金句强调） | 产物不同：它出图，我们出文字稿。 |
| `MAX_TIMES_PER_IMAGE = 7` 一类版式常量 | 与文字转写无关。 |

不过它的 `validate_repo.py` 里有一条我们**该抄**：**检查所有文档里的相对链接是否存在**。我们的 `check-anchors.mjs` 只校验锚点，不校验文件是否存在；README 里 `docs/xxx.md` 这类链接写错，现在没人拦。

## 4. 三个与直觉相反的实测

汇总上面散落的数据，这三条是本轮真正的产出：

**① 字幕带的上下边界可以零依赖自动定位，但选簇规则必须重写。**
同一套掩码，压成列是「左右边界」，压成行是「上下边界」。它的「取最大簇」在整帧上会被大面积亮区骗走（实测选中画面上方 0.167–0.231，真值 0.884–0.936）；加三条先验后 6/6 正确。成本 14 ms/帧（640 宽）。

**② 「相邻句子整帧差异 5% 以上」不成立，实际只有 1% 左右。**
它的默认阈值 0.005 因此只有 2 倍余量。换到字幕带口径是 7%–10%，余量 15–21 倍。**去重必须用带内口径**，否则相似短句会被误合。

**③ 「两段 seek 防错帧」在 H.264 上未复现。**
三种时间点、逐像素 0 差异；单段更快（72 vs 76 ms）。保留可以，理由要改成「索引异常兜底」。

## 5. 反向：我们的产出正好是它的输入

这一节换个方向看——与其把它的取帧能力搬进来，不如先把**接口对齐**，让两个 Skill 直接串起来。

它需要的两种输入：

```jsonc
// render（原生字幕模式）：每张图 5 个严格递增的时间点
{"images": [{"title": "标题只用于文件名", "times": [61.6, 69.3, 75.0, 82.4, 88.8]}]}

// render-script（脚本字幕模式）：时间点 + 已核对台词
{"lines": [{"t": 61.6, "speaker": "主持人", "text": "第一句已核对台词"}]}
```

我们的输出（`transcribe.py`）：

```jsonc
{"segments": [{"s": 61.24, "e": 66.80, "t": "这一期我们聊三件事"}]}
```

**映射是一对一的**：`s`（或 `(s+e)/2`）→ `times[]` / `t`，`t` → `text`。一个十几行的转换脚本就够，不需要改任何一边的代码。

而且它的 `SKILL.md` 明确写了要复用上游：

> 字幕轨或 Whisper：生成带时间戳的内容索引。
> 复用上游已经下载的视频、文字稿和缓存，不重复消耗网络或转写成本。

**所以最省力的组合不是移植，是串联**：我们负责把视频变成带时间戳的文字稿，它负责把选定的句子变成图。这两件事谁都不用重写。

如果要做，我建议就做一个 `scripts/to_quote_manifest.py`（约 60 行，零依赖）：读我们的 JSON + 一个句号列表（或行号范围），吐出它的 `lines` JSON。属于「跨 Skill 适配」，不是新功能，也不违反零依赖。
