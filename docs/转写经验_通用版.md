## 0. 一页速查

### 推荐组合

| 角色 | 方案 | 用在哪 |
|---|---|---|
| **主力** | faster-whisper + `large-v3-turbo`，GPU / float16 | 所有正式稿，尤其含英文缩写、产品名、人名的中英混读内容 |
| **补充** | SenseVoice q8 GGUF 独立运行时（纯 CPU、无需 Python / torch） | 批量快速预览、当「真正异源」的第二意见、只核分歧处 |
| 对照 | `large-v3` 完整版，GPU | 疑难片段复核；**不要当主力** |
| 应急 | turbo / CPU / int8 | 显卡不可用时的回退路径 |

### 开工前五条自检

1. `nvidia-smi` 能看到显卡 → 有卡就别用 CPU。
2. `python -c "import faster_whisper, ctranslate2; print(faster_whisper.__version__, ctranslate2.get_cuda_device_count())"` → 能出版本号且设备数 ≥1。
3. 模型目录存在，且含 `config.json` / `preprocessor_config.json` / `tokenizer.json` / `vocabulary.json` / `model.bin` 五个文件。
4. CUDA 的两个算子库（cublas / cudnn 的 DLL）在 Python 的 site-packages 下找得到，**多数情况下在用户级目录，不在解释器目录**。
5. `ffmpeg -version`、`ffprobe -version` 都在 PATH。

> 前三条任一不过，先修环境，别急着转写；已装好的环境不要重复安装、重复下载。

### 五件绝对不要做的事

- **不要关掉 `initial_prompt`**：关掉后标点密度几乎归零（掉到 0–0.1/百字），整篇糊成一片。
- **不要拿四个数字指标当「合格」**：它们查不出凭空冒出来的内容，也查不出开头被整段替换。
- **不要把 turbo 和 large-v3 当两个独立引擎做交叉验证**：turbo 是 large-v3 的解码器剪枝版（32→4 层），共享同一个编码器和训练数据，错误高度相关。
- **不要照抄排行榜或别人的倍速**：题材不同结论会反转，见 §1.8。
- **不要在可用内存吃紧的机器上装 torch 系大模型**：内存往往比显存更早成为瓶颈。

### 转完必做三查（比任何指标都重要）

1. **查开头 30 秒**：有没有把提示语原文念进正文、有没有片头话术、真实开场是不是被整段吃掉。
2. **查结尾 30 秒**：有没有凭空冒出「谢谢大家 / 感谢观看 / 请不吝点赞…」，最后一段的结束时间是不是**超过了音频总时长**。超过就是多出来的幻觉段，不是「尾部空为负 = 合格」。
3. **查中间长间隙**：任意相邻两段时间间隔 **> 8 秒** 直接标红，回听该区间，或拿异源方案的输出对照。

> 这三项是硬检查，不是参考值。不同配置、不同素材上分别中过招，属于系统性风险，不是偶发。

## 1. 方案选型

### 1.1 主力：faster-whisper（SYSTRAN）+ Whisper large-v3-turbo（OpenAI），GPU

选它的理由：底层是 OpenNMT 的 CTranslate2 推理引擎，CPU 可用、不依赖 torch、GPU 支持好、能直接吃普通目录里的模型权重（不走缓存）、**默认输出段级起止时间戳**便于对齐。

> ⚠️ 别把「段时间戳」写成「词级时间戳」：`word_timestamps` 默认 `False`，输出里每段只有起止时间和文本；要词级需显式打开，会更慢、更占资源（见 §3）。写能力描述前先看一条真实 JSON 的字段。

主要短板：**专有名词靠软引导，没有原生热词**；中文长音频上不一定优于国产模型；长静音或试麦段可能凭空生成内容。

### 1.2 补充：SenseVoice（QwenAudio）+ FunASR GGUF 运行时（CPU）

模型是 QwenAudio（原 FunAudioLLM）的 SenseVoiceSmall，独立运行时与 q8 GGUF 量化由 modelscope/FunASR 项目发布（基于 ggml-org/llama.cpp）。一个可执行文件 + 一个模型文件 + 一个静音切分模型，**不需要 Python、不需要 torch、纯 CPU、零显存**。速度最快、内存最省、标点最密，适合：

- 大批量先快速过一遍，看个大概；
- 与主力各转一遍，**只人工核对两边不一样的地方**；
- 显卡被别的事占着时继续干活。
- 主力输出出现长时间空隙时，用它对照该区间是否另有内容（**漏段探测**）。它偶尔能补出另一边漏掉的片段，但**通常不完整、文本也可能较乱，只能当线索**，不能当补回来的正文。

必须说清的限制：

- **中英混读的专名明显弱于主力**（英文缩写、产品名容易听成音近汉字）。重要稿子不能只用它。
- **输出没有任何可用时间信息**（运行时只给一个覆盖全长的整段，看似有起止时间其实是占位），只能当纯文本参照，不能做时间轴对齐或字幕，**也不能用它判断「尾段是否越界」**。
- 权重许可是 **FunASR Model License**（代码仓库是 MIT，两者要分开看），商用前核对署名等义务。

### 1.3 对照：large-v3 完整版

同音词、人名上偶尔比 turbo 稳，但**速度约为主力的 1/3、内存与显存占用约为 2–3 倍**，容易顶到资源红线。它还会**引入主力没有的新毛病**（开头把提示语念进正文、结尾生成片尾话术）。只留作疑难片段复核，别当日常主力；**定向复核时开头和结尾都要看**，别只盯着有疑问的那一段。

### 1.4 应急：turbo / CPU

不占显存是唯一优点，速度约为主力的 1/7。只在显卡不可用或做小规模验证时用。

### 1.5 需要改造才能用 / 不推荐

| 方案 | 问题 |
|---|---|
| SenseVoice int8 ONNX（k2-fsa/sherpa-onnx 导出，Python 包） | 与 1.2 是同一套权重的不同装法，但明显吞字、更慢、更占内存；被独立运行时全面压制 |
| Paraformer 中文 ONNX（modelscope/FunASR 模型，sherpa-onnx 导出） | 输出**一个标点都没有**，不能直接出可读稿，必须外接标点 / 数字规整模型 |
| 云 ASR API | 要联网、要账号、长音频切分麻烦；离线约束下不进选型，只可作真值对照 |
| 同源 whisper.cpp 权重（ggml-org/whisper.cpp） | 与主力同一套模型，不构成独立第二意见 |

### 1.6 明确排除

需要 torch / Transformers / vLLM 的整套方案（FunASR Python 版、QwenLM 的 Qwen3-ASR、m-bain 的 WhisperX、说话人分离）、7B 级以上的端到端语音模型。理由：**可用运行内存不足时，光是把依赖装完就吃不消**，且 8 GB 显存装不下大模型。等第一轮证明「异源确实有收益」、并换到内存更空闲的机器再单开一轮。

### 1.7 参考量级对比

> 下表只用于判断**相对关系**（谁快、谁省、谁标点多），数字随机器和素材变化，不要当性能指标。

| 方案 | 速度 | 运行内存 | 显存 | 标点密度 | 中英混读专名 | 能单独出正式稿 |
|---|---|---|---|---|---|---|
| 主力 turbo / GPU | 约 19× | 约 +1.2–1.6 GB | 约 +1.9–2.1 GB | 中等 | **最稳** | ✅ |
| large-v3 / GPU | 约 6× | **约 +3.0–3.1 GB** | **约 +3.8–3.9 GB** | 中等 | 同音词略好 | ✅ 能，但代价大（不作主力） |
| turbo / CPU | 约 2.6–2.9× | 约 +1.4–1.5 GB | 0 | 中上 | 同主力 | ✅ 慢 |
| **SenseVoice q8 GGUF / CPU** | **约 27–28×** | **约 +0.36–0.37 GB** | 0 | **最高** | **弱** | ⚠️ 预览 / 对照 / 漏段线索 |
| SenseVoice int8 ONNX / CPU | 约 8.7× | 约 +1.3 GB | 0 | 中上 | 弱、且吞字 | ❌ |
| Paraformer int8 ONNX / CPU | 约 11.5× | 约 +0.9 GB | 0 | **0** | 弱 | ❌ 需后处理 |

> 「×」指实时倍率：1 分钟的音频用 60÷倍率 秒转完。内存 / 显存取**批次最大峰值增量**（不是典型值），样本规模与后台负载不同会有约 30% 波动，别当硬指标。

### 1.8 三条选型原则

1. **同源不等于独立**：要真正独立的第二意见，必须换不同架构、不同训练数据的引擎。同系列两版一起听错，不能推断「这个词确实难」。
2. **题材决定排名**：短、竖屏、术语密集、中英混读的口播上，Whisper 系往往比中文模型稳；长会议、长朗读上中文模型可能更好。网上榜单多测后者，**别外推到自己的素材**。
3. **内存比显存更要命**：可用运行内存 < 5 GB 时，先排除一切要装大依赖的方案；所有方案串行跑、一次只加载一个模型、测完立即释放。

## 2. 标准流程（从素材到成稿）

> 路径一律用占位符，开工第一步先确认项目根目录，别把脚本和素材放在不同目录还互相引用相对路径。
>
> **开测前先回答四个问题**（比选模型更优先）：① 这一轮到底要回答什么（选型 / 调参 / 质量 / 资源）？② 判分依据在不在手边（人工稿、官方字幕，还是都没有）？③ 指标口径和资源红线定没定？④ 产物放哪、会不会覆盖旧结果？四个都答完再排执行矩阵。

| 步 | 做什么 | 要点 |
|---|---|---|
| 0 | 确认项目根 + 素材清单 | 先做只读体检：有没有音轨、精确时长、格式、体积；**没有音轨的素材单独告知，不要硬跑** |
| 1 | 建目录 | `<根>/原始素材`（只读）、`<根>/逐字稿`、`<根>/成稿`、`<根>/_tools` |
| 2 | 环境自检 | 跑 §0 的五条命令；已就绪就跳过安装与下载 |
| 3 | 抽音频 | `ffmpeg -y -i "<素材>" -vn -ac 1 -ar 16000 -c:a pcm_s16le "<输出>/<编号>.wav"`；**只抽一次，多方案共用同一份输入**，保证可比 |
| 4 | 主力转写 | 参数见 §3；输出 `.json`（结构化）+ `.md`（带时间戳可读版） |
| 5 | 补充方案转写（可选） | 见 §4；用于快速预览或第二意见 |
| 6 | 对齐差异 | 两份文本归一化后算差异，**人工只看分歧处和长间隙区间**，省时间 |
| 7 | 质检 | 见 §5；四个指标只当粗筛，必须补首末段检查 |
| 8 | 精编 | 建术语表统一替换专名；补标点、数字规整；原始稿保留不覆盖 |
| 9 | 留痕 | 记录模型版本、参数、耗时、素材时长、复核命令、许可证；便于下次复现 |

> ⚠️ **转写链路从头到尾只处理音频，从不做图像识别。** 第 3 步用 FFmpeg 把视频里的声音抽成 WAV 之后，画面就不再参与任何识别计算。文中提到的「抽帧」是 §5 的另一条**可选质检旁路**，只在没有文字稿、又想做量化对照时才启用，详见 §5.5。

### 2.1 素材来源的通用提醒

- **先确认文件里真的有音轨**：`ffprobe -show_streams` 看不到 audio stream 就不要硬跑。部分视频站把音视频分开存放，某些编码版本（如 HEVC 的 mp4）只有视频流，音频是独立的一条流，需要单独取；能拿到 h264 + aac 的封装文件最省事。
- **下载站点资源要带正常的请求头**（来源页 Referer + 浏览器 UA），否则可能拿到 403 或验证页。
- **遇到登录墙不要硬绕**：改分页参数常会破坏签名、返回验证页。让用户自己把素材下载好、只做转写，反而更快。
- 上述站点行为属于**一次性观察**，站点改版后要重新确认，别写进流程当永久规则。

### 2.2 批处理工程要点

- 用 `glob` 取列表 + 状态文件记录已处理项，实现**断点续跑**，分批投喂不重复跑。
- 循环里每个文件独立 `try/except`，失败只记日志并跳过，不中断整批。
- `ffmpeg` 设足超时（长文件 900 s 起），防止异常文件卡死。
- 状态文件别和主流程共用一个：后补批次用独立状态文件，避免口径混算。
- 汇总脚本如果会**覆盖已有报告**，重跑前先备份，或给脚本加集数白名单锁死口径。
- **每轮新建独立输出目录**，别覆盖上一轮；固定一份样本清单（样本 ID ↔ 源文件 ↔ 时长 ↔ 统一 WAV），产物用 `<配置>_<样本ID>` 命名，全程只用 ID。
- **原始输出只写一次、不手改**；任何修正放到下游脚本里做，保证结果可追溯。

## 3. 主力转写参数（可直接抄）

| 参数 | 值 | 为什么 |
|---|---|---|
| `language` | `zh` | 避免自动识别摇摆 |
| `beam_size` | `5` | 质量与速度的平衡点 |
| `vad_filter` | `True` | 跳过长静音省时间；**但挡不住开头幻觉** |
| `min_silence_duration_ms` | `300–400` | 太小切碎句子，太大漏话 |
| `condition_on_previous_text` | `False` | 防止前一段的错误在后续段落循环放大 |
| `initial_prompt` | `以下是普通话的句子，请使用简体中文，并加上标点符号。` | **必须保留**，关掉后标点密度掉到接近 0（0–0.1/百字） |
| `temperature` | `0.0 / 0.2 / 0.4` | 是**段内**按重复率 / 置信度阈值逐级降级，不是整次转写失败后重跑 |
| `word_timestamps` | `False`（默认） | 只给段级起止时间；设 `True` 才输出词级，速度更慢、占用更高，非必要不开 |
| `device` / `compute_type` | `cuda` / `float16` | 有卡就一定用 GPU |
| 回退 | `cpu` / `int8` / `cpu_threads=8` | 写进 `try/except Exception`，见下 |

### 3.1 关于 `initial_prompt`

- 它确实在提供标点：关掉后输出标点密度从约 2–2.4/百字掉到**接近 0（0–0.1/百字）**，整篇几乎无标点。
- 但它**不是热词**，也不保证简体和断句。**「不加就标点稀疏」已有对照**（关掉后从约 2–2.4/百字掉到 0.10）；但「不加会出繁体」未做系统统计，别当结论。
- **副作用要盯**：提示语原文可能被整段复读进正文；也见过把片头话术（「请不吝点赞、订阅、转发…」）当成正文。把这些句子列进 §5 的检查关键词。
- `hallucination_silence_threshold`（1.2.1 起提供，默认 `None`）只缓解**静音段**幻觉、需配合 VAD，对真实语音段未必触发。留着可以，**别指望它替代人工检查**，也不要因为一次没看出效果就断言参数无用。

### 3.2 GPU 的隐形依赖（最大的坑）

现象：指定 `cuda` 后**模型能加载成功**，一推理就报 `Library cublas64_12.dll is not found or cannot be loaded`。

原因：CTranslate2 走 CUDA 12，运行时按名字动态加载 cublas / cudnn 的 DLL，它们不在系统 PATH 里。少任何一个都是「加载成功、推理失败」。

做法（顺序是关键）：

1. 确认两个 pip 组件已装（`nvidia-cublas-cu12`、`nvidia-cudnn-cu12`），DLL 通常在**用户级** site-packages 的 `nvidia\cublas\bin`、`nvidia\cudnn\bin`。
2. **在创建 / 推理 WhisperModel 之前**，对每个 bin 目录执行 `os.add_dll_directory(目录)`，并把目录前插进 `os.environ['PATH']`。
3. 真实要求是「**加载模型之前**」，不是字面意义的「任何 import 之前」——放在 `import faster_whisper` 之后也照样能跑通。
4. 显卡驱动只提供 CUDA 运行时，**算子库来自这两个 pip 包**，别只装驱动。

### 3.3 一定要写回退

```python
try:
    segments, info = model.transcribe(...)
    segs = list(segments)          # 强制消费生成器，让异常在这里抛出
except Exception as e:             # 不要写裸 except:
    model = WhisperModel(path, device="cpu", compute_type="int8", cpu_threads=8)
    segments, info = model.transcribe(...)
    segs = list(segments)
```

> 回退后把**实际使用的设备**写进输出，别让 JSON 里还记着 `cuda`。

### 3.4 版本锁定

- 若锁在 faster-whisper **1.2.1 发布版**：`pin av<19`（`av` 即 PyAV-Org 的 PyAV）、暂不升 Python 3.14。上游主分支已修 PyAV 19 / 3.14 的适配，但尚未随该发布版提供——这是「发布版滞后」，不是「项目停更」。
- 想确认上游状态，查 GitHub API / PyPI 的 `pushed_at`、最新 release、issue 状态，**不要引用别人几个月前写的维护快照**。
- **「上游主分支已修」不等于「你装的发布版已修」**：版本锁定以本机 `pip show` 为准，别拿仓库状态代替安装状态。

## 4. 补充方案怎么用（SenseVoice q8 GGUF 独立运行时）

**拿到的东西**：一个 Windows 可执行文件 + 一个 q8 量化的模型文件 + 一个静音切分模型；一次性调用，无需常驻服务。

**典型调用**（注意路径写法）：

```
cd <可执行文件所在目录>
llama-funasr-sensevoice.exe -m <模型.gguf> --vad <vad.gguf> -a <相对路径/音频.wav>
```

四个必须注意的点：

1. **中文 / 非 ASCII 路径**：这类原生二进制常把路径读成乱码，表现为「手工试跑成功、批量全失败」。做法是**把工作目录切到程序所在目录，一律传相对路径**。
2. **日志和正文可能打在同一行**（形如 `正文内容[sensevoice] building graph...`）。解析时按日志标记切分、只取前面的正文，否则字数会虚高一倍。别只看「整行是否以日志开头」。
3. **没有可用时间信息**：运行时只给一个覆盖全长的整段，看着像有起止时间其实是占位。只能当纯文本参照，不能做时间轴对齐、不能出带时间码的字幕，也不能据此判断尾段越界。
4. **许可证分开看**：代码 MIT，权重是 FunASR Model License；第三方转换的 ONNX / GGUF 包可能标不同条款，逐个核对。

**定位与验收**：批量快速预览、异源第二意见。重要稿子以主力为准；涉及英文缩写、产品名、人名的段落直接采信主力输出。

## 5. 质检

### 5.1 四个数字指标只能当粗筛

| 指标 | 算法 | 参考范围 | 异常含义 |
|---|---|---|---|
| 字符密度 | 总字数 ÷ 分钟 | 200–450 字/分 | 明显偏低 → 漏转或静音多 |
| 尾部空 | 时长 − 最后一段结束 | < 10 秒 | 很大 → 结尾被截断；**若算出来是负数（末段 end 超过音频时长），那是「多出来的幻觉段」，必须标红，不能当合格** |
| 最大间隙 | 相邻段间隔 | < 8 秒 | **> 8 秒必查**：四项里唯一能抓到「中间整段漏掉」的；回听该区间或对照异源输出 |
| 段数 | 段数 ÷ 分钟 | 15–40 段/分（粗筛） | 太少但密度正常 → 可能只是长句；实测切分更碎的配置上限可到 **50–55 段/分**，别把 40 当硬上限 |

**「不用听完，看四个指标就够」是错的**。这四个数只查「有没有漏」；已知案例中，开头 30–40 秒被整段替换成凭空生成的内容、或整段丢失时，四项全部正常通过。另注意别拿自己数据反推阈值再说「全部合格」，那是同义反复。

> 四项里，**最大间隙是唯一在实测中真抓到过漏段的**，应升级为硬检查；另外三项（尤其尾部空）在「多出来的幻觉段」面前会完全失灵。

### 5.2 必须补的检查

1. **首末段人工看一眼**：开头 30–40 秒、结尾 30 秒，重点看重复、串台、提示语原文。**开头若只剩提示语回音，通常意味着真实开场被整段吃掉**（约 30 秒），直接标红并回听。
2. **重复片段 / 压缩比**：单段字数异常高、同一短句重复几十次，直接标红。
3. **提示语泄漏关键词**：把本项目用的提示语原文，以及常见片头话术列成关键词表。
4. **与字幕或画面文字对照**：有官方字幕时那才是真值；只有烧录字幕时，可用 OCR 工具（如 RapidAI/RapidOCR）**按 1 fps 抽样**画面做参考（不是逐帧、更不是 ASR 的一步），且**必须先过质量门槛**（见 5.3 / 5.5）。
5. **随机抽听**：按编号抽样，别只靠数字。
6. **自动检查规则先人工验几条命中样例再信**：过粗的规则（「特别长的一段」「高频两字词」）会把正常长句和「任务」「怎么」这类常用词误报成幻觉。
7. **尾段越界硬检查**：最后一段 `end > 音频时长 + 0.5 s`，或末两段出现「谢谢大家 / 感谢观看 / 请不吝点赞 / 订阅 / 明镜 / 字幕由」等片尾话术，直接标红。**尾部空算出来是负数时不要当合格**，那正是越界幻觉段。
8. **中间长间隙必查**：任意相邻段间隔 > 8 秒直接标红，回听该区间，或拿异源方案的文本对照该处有没有内容。注意同源的两个版本常一起漏，别用同源做这个对照。**这类区间实测音量与正常段落只差几个 dB、并不是真静音**，别默认「静音检测跳过是对的」。
9. **统计前先做 NFKC 归一化**：标点密度、字数等一律先归一化再统计，否则 U+FE50 / U+FE51 这类小型标点变体会被漏计，可能把有标点的稿子误报成「0 标点」。

### 5.3 有没有标准答案，决定能报什么

| 情况 | 参照物 | 能报什么 |
|---|---|---|
| ① 随素材给了逐字稿 / 官方字幕文件 | near-gold（人工稿可能是润色版，只用于语义与专名核对） | 可算字错率，须标注 near-gold |
| ② 只有烧录字幕、无文字稿 | 对画面**按 1 fps 抽样**（每秒 1 张，不是每一帧）做 OCR 得到 silver；相邻帧文本相同则去重合并 | 先过质量门槛：与转写输出的**字数比**、**内部重复率**。不合格就丢弃，不能硬算 |
| ③ 都没有 | **不硬算字错率** | 只报开头幻觉、重复片段、标点密度、数字规整、段结构、术语命中、资源与速度，以及多方案间的一致性（**注明同源方案会高估一致性**） |

> 典型失真：画面里有固定标题、装饰字、滚动字幕，OCR 会把它们全算成正文，得到的「参考文本」比转写结果长好几倍。拿这种尺子量出来的准确率是假的。**宁可写「这一项测不出来」，也不要报一个好看的百分比。**

**归一化与字错率**（所有比较共用，写进脚本常量）：全角→半角 → 英文小写 → 删除全部标点与空白 → 数字统一为阿拉伯数字（中文数字不转，单独标注）→ 字错率 = 字符级编辑距离 ÷ 参照长度。中文按字算，可自实现动态规划，不必引入新依赖。繁简转换若无对应库，明确标注「未转换」。

**术语命中**：有术语表才做量化；没有就从各方案输出里抽出中英混读词列成分歧清单，只作定性案例，不计入验收。

### 5.4 常见的幻觉形态

- 开头重复「喂? 喂?」之类试麦词，一口气几十上百字；
- 把提示语原文整段念进正文；
- 冒出不属于本素材的片头 / 片尾话术（「请不吝点赞、订阅、转发…」）；
- 开头约 30 秒真实内容被整段吃掉，四个数字指标依然全过；
- **结尾凭空生成「谢谢大家 / 感谢观看 / 请不吝点赞…」等片尾话术，且最后一段的结束时间越过音频结尾十几到几十秒**——此时「尾部空」算出来是负数，四个指标反而全过；
- 异源轻量方案也可能在结尾生成不属于素材的句子；因为它没有时间戳，**无法用「尾段越界」判定，只能人工读末尾**；
- 中间十几秒的真实内容整段消失，只留一个长间隙；密度、段数、尾部空都看不出来。

> 结尾幻觉、中间漏段和开头幻觉一样，都**不会**让四个数字指标报警；「转完必做三查」（§0）就是为此设的。

### 5.5 转写与画面：两条互不依赖的链路

**这是最容易误会的一点：语音识别不看画面，一帧都不看。**

| | 主链路：语音识别（ASR） | 旁路：质检参照（可选） |
|---|---|---|
| 输入 | 16 kHz 单声道 WAV（纯音频） | 视频画面抽样得到的图片 |
| 是否必须 | 必须，所有方案都要 | **可选**；仅在「没有逐字稿 / 官方字幕，又想算字错率」时才做 |
| 采样 | 整段音频全量 | **1 fps**（每秒取 1 张），相邻帧文本相同则去重；**不是视频的每一帧** |
| 用到的东西 | faster-whisper、SenseVoice 等 ASR | OCR，如 RapidAI/RapidOCR（Apache-2.0） |
| 产出 | 逐字稿 + 时间戳 | 一份「参考文本」（silver），且必须过质量门槛 |
| 与转写的关系 | 独立 | **完全独立**：OCR 结果不参与、也不影响任何模型的识别计算 |

所以「抽帧」不是转写流程的一步，更不是「每帧画面都做图像识别」——一段 3 分钟视频按 1 fps 只抽约 180 张图，而视频原始帧率通常是 25–30 fps（约 4500–5400 帧），两者差一个数量级。

这条旁路还很容易失效：画面里的固定标题、装饰字、滚动字幕都会被 OCR 当成正文，参考文本可能比转写结果长好几倍。所以 §5.3 规定**必须先过质量门槛**；不合格就整条放弃，不拿它算准确率。本手册不推荐把它当常规步骤。

## 6. 专有名词：调参解决不了，靠流程补

**固有短板**，常见错法：英文缩写听成音近汉字、产品名听成常见词、人名听成同音词、行业术语听成字面词。例如 `Harness→Hannis`、`Agent Loop→EdgeLoop`、`LangChain→LongChang`、`RAG→ROG`、`意图识别→一图识别`、`召回率→招回率`。

补救手段，**按可靠性排序**：

1. **看字幕 / 原始文稿**：那是真值，别猜。
2. **换真正异源的引擎拿第二份结果**：同源两版不算。
3. **上下文推断**：结合前后句判断该是哪个词。
4. **建术语对照表**：把音译和实际词记下来，精编稿统一替换，原始稿保留。
5. **原生热词**：部分引擎支持解码期热词或文本偏置，比提示语软引导可靠；但词表要克制，热词会把普通词误写成专名。注意区分「开源权重」与「闭源 API」的能力，别把 API 的特性算到开源模型头上。

> 血泪教训：曾凭「两次转写都落在同一个音上」推断对了一个词，又用同样方法推断错了一个词——**同音只能提高置信度，不能替代真值**。同源模型连这点置信度都要再打折。「两版一致就采信」必须改成「一致只降低风险」。

## 7. 环境与资源

### 7.1 依赖清单（参考版本 + 复核方式）

> 版本号只作量级参考，**用下面命令自己查，别照抄**。环境快照会漂移，写明核实日期。

| 组件 | 参考 | 复核命令 |
|---|---|---|
| Python | 3.13.x | `python -V`（PATH 里可能有多个 Python，显式写绝对路径最稳） |
| faster-whisper | 1.2.1 | `python -c "import faster_whisper; print(faster_whisper.__version__)"` |
| ctranslate2 | 4.8.x | `python -c "import ctranslate2 as c; print(c.__version__, c.get_cuda_device_count())"` |
| onnxruntime / numpy | 随依赖带入 | `pip show onnxruntime numpy` |
| cublas / cudnn DLL | 用户级 site-packages 下 | `python -c "import site; print(site.getusersitepackages())"` 后查 `nvidia\*\bin\*.dll` |
| ffmpeg / ffprobe | 已在 PATH | `ffmpeg -version` / `ffprobe -version` |
| torch | **不该装** | `python -c "import importlib.util as u; print(u.find_spec('torch'))"` → `None` |

模型体积参考（客观值，可用于估磁盘）：turbo 约 **1.51 GiB**、large-v3 约 **2.88 GiB**、合计 **4.39 GiB**（目录 5 个文件口径；单看 `model.bin` 略小）。全文体积统一用 GiB（1024³），DLL 用 MiB。

GPU 相关：`nvidia-smi -q` 里 `Default Power Limit` 是默认值，**别把它当当前限制**；`--query-gpu=power.limit` 可能返回 `N/A`。倍速波动受后台负载、首次加载、VAD 命中、音频内容影响，没有同步记录 `clocks.sm` / `power.draw` 就别做单因素归因。

### 7.2 资源护栏

- **串行**：一次只加载一个模型，跑完立即释放；不要同时跑两套。GPU 方案和纯 CPU 方案并发时，内存 / 显存读数会互相污染，资源结论就不可信。
- **测峰值要连续采样**：每 0.5–1 秒采一次进程树内存 + `nvidia-smi` 显存，取「全程最大值 − 基线」。**前后各采一次只能看到跑完后的残留**，测不到峰值。
- **熔断线**（按机器实际调整）：可用运行内存 < 2 GB 或可用显存 < 3 GB 直接停；单方案运行内存增量 > 1.5 GB 要重新评估。
- **磁盘预算**：下载包 + 解压后 + 运行时是**双份甚至三份**空间，别只按压缩包大小估。测完及时清掉不再需要的下载物。
- **缓存目录**：把 `TEMP` / `TMP` / `PIP_CACHE_DIR` / 模型缓存都指到工作区，避免下载途中吃掉系统盘。

### 7.3 安装与下载

- **优先国内镜像**：默认源经常几分钟无进展，换镜像后可能几秒完成。
- **隔离安装**：`pip install --no-cache-dir --no-deps --target <工作区>/pylibs <包A> <包B>` + `PYTHONPATH=<工作区>/pylibs`，不污染全局环境、删目录即回滚。
- **`--no-deps` 要手动补齐依赖**：有些 Python 包只是外壳，真正干活的在另一个核心包里。装完**先跑一次 import 冒烟测试**，不过就整组跳过，别浪费后面时间。
- **记录 URL / 版本 / 哈希**，否则下次重跑结果对不上。
- **官方源可能停滞**：大文件用镜像 + 多线程分片（Range 请求、按已有偏移续传、先写 `.partN` 再合并）。
- **不要用 HF 默认缓存目录**：Windows 未开开发者模式时建不了软链接，缓存会存两份。更省事的做法是**下载到普通目录，直接把目录路径传给模型构造函数**。
- **许可证分两列**：代码许可证 ≠ 权重许可证。「代码 MIT / 权重自定义、商用需署名」这类组合很常见，别一律当 Apache-2.0。

## 8. 踩坑清单

> 每条都是「现象 → 原因 → 做法 → 预防」。已泛化，不含具体素材或路径。
>
> **排查前先分归属**：问题出在模型行为、参数组合、脚本 / 解析、还是指标口径？四者对应完全不同的动作——换模型 / 改参数 / 改脚本 / 改指标。分不清就乱试，最费时间。

### 8.1 安装 / 下载

| 现象 | 原因 | 做法 | 预防 |
|---|---|---|---|
| 装一个几 MB 的包几分钟没动静 | 默认源在国外 | 换国内镜像 | 国内机器先试镜像，别死等 |
| 装完 `import` 直接失败 | `--no-deps` 跳过了真正干活的核心包 | 两个包一起装 + import 冒烟测试前置为硬门槛 | 装完先验收，再进主流程 |
| 大文件下到一半断掉 | 单线程、无续传 | 分片 Range 下载、按已有偏移续传、先写分片再合并 | 先探地址可达性，再后台拉 |
| 磁盘比预算多吃几百 MB | 压缩包、解压目录、另一套运行时都留着 | 测完清掉不再需要的下载物 | 预算按「双份」算 |
| 缓存把系统盘吃紧 | 临时目录默认指到系统盘 | 所有缓存变量指到工作区 | 开工前统一设环境变量 |

### 8.2 自己写的工具

| 现象 | 原因 | 做法 | 预防 |
|---|---|---|---|
| 一整批转写全失败，但模型没问题 | 自己写的资源采样辅助函数崩了（Windows 取当前进程返回 `-1`，被 ctypes 当无符号数溢出） | 显式声明 `argtypes`、用固定的伪句柄常量 | **新写的辅助工具先拿 1 条最小样本单跑一次，再上批量** |
| 汇总表整片空白 | 按完整编号精确匹配，实际编号带后缀 | 改前缀 / 分组匹配 | 先打印一条真实数据看清格式 |
| 自动质检报一堆幻觉，一看全是误报 | 规则太粗：「特别长的一段」命中正常长句、「高频两字词」命中常用词 | 剔除这两类规则，只留有证据的关键词命中 | 先人工看几条命中样例再信数字 |
| 结果名对不上、差异度算不出来 | 分组字典用了错的键名 | 统一命名规范，先验证一条 | 写汇总前先看一条原始输出结构 |
| 重跑汇总把旧报告覆盖 | 脚本直接 `open(..., "w")` | 重跑前备份，或锁死口径再写 | 汇总脚本默认写新文件 |

### 8.3 外部程序

| 现象 | 原因 | 做法 | 预防 |
|---|---|---|---|
| 手工试跑成功、批量全失败，报路径乱码 | 原生二进制不能正确处理非 ASCII 路径 | 工作目录切到程序目录、一律相对路径 | 拿一条带中文的路径先试 |
| 字数虚高一倍 | 程序把运行日志和转写正文打在同一行，按「整行过滤」没清掉 | 按日志标记切分、只取前面正文 | 先看一眼原始输出，别假设格式 |
| 换模型后启动报错 | 不同模型的构造参数名不一样（有的叫 `model`，有的叫模型名） | 写之前用 `inspect.signature` 核对 | 换模型先查签名，别照抄 |
| 想做时间轴对齐却没时间戳 | 部分轻量运行时只给纯文本 | 这类方案只当文本参照，对齐仍用主力输出 | 选型时先确认输出结构 |

### 8.4 判断方法（最危险，会得出假的漂亮结论）

| 现象 | 原因 | 做法 | 预防 |
|---|---|---|---|
| 拿画面字幕算准确率，结果明显不对 | 固定标题、装饰字、滚动字幕被混进参考文本 | 加质量门槛（字数比 + 重复率），不合格自动放弃计算 | **尺子不准时宁可不出数字** |
| 原定的「术语命中率」算不了 | 没有术语表 | 该验收项不参与判定，只留定性案例 | 开测前先确认判分依据在手边 |
| 专门为某个毛病设计的开关，测完判不出好坏 | 样本里根本没出现那个毛病 | 如实写「得不出结论」，不要说参数无效 | 想验证什么，样本里就得有什么 |
| 长音频结论站不住 | 样本全是短素材 | 标注「不外推到长音频」 | 先体检样本再定矩阵 |
| 把估算写成实测、把设计写成既成事实 | 多次笔记叠加没归并 | 每个数字标出处；无来源的标「估算 / 推断」 | 写「数据出处」小节，逐条钉到文件或命令 |

### 8.5 Windows / Agent 工具环境

| 现象 | 归类 | 做法 |
|---|---|---|
| 控制台中文乱码（stdout 是 GBK/OEM、控制台按 UTF-8 显示，方向别写反） | Windows | 结果写文件再用 UTF-8 读，别靠控制台看 |
| 后台任务输出为空 | 跨平台 | `print(..., flush=True)` 或直接落盘 |
| 脚本里反引号报错 | Agent 工具环境 | 用数组 `join` 拼文本，别用模板字符串包代码块 |
| 覆盖文件被拒 | Agent 工具环境 | 先读一次再写 |
| 改现有脚本前没留副本 | 流程 | 复制进工作区再改，别动原工具 |
| 批处理与单文件脚本的超时值不同 | 流程 | 按最长素材设，别把两套脚本的数值混写 |
| 一条命令里又有中文路径、又有 JSON 和多层引号，解析直接失败 | 命令 / 工具环境 | 超过几行的逻辑一律落成脚本文件再跑；命令行里不拼 JSON、不嵌套三层引号 |
| 长任务在工具里等全程，结果工具自己先超时 | 工具环境 | 长任务一律后台跑 + 分次看日志；单次等待时间不能设得比工具总时限还长 |
| 首条转写很久没输出，以为挂了 | 工具环境 | 先看日志文件 / 后台任务状态；别拿「没输出」判断失败，脚本里 `print(..., flush=True)` 或直接落盘 |
| 同一条命令换个 shell 版本就报错 | 跨平台 | 不假设 shell 版本一致；先在目标环境跑一条最小样例；统计与 JSON 解析交给 Python，别用 shell 管道拼对象 |
| 结果文件里的中文正常、控制台却乱码 | Windows | 结果统一 UTF-8 写文件再读；Python 加 `-X utf8`，日志 / CSV / JSON 全部 UTF-8 |

### 8.6 三条通用教训

1. **辅助工具先单跑一条再上批量**——否则一个小函数能把整批主任务全带翻。
2. **「我没找到」不等于「它不存在」**——取证先确认项目根目录与一手来源；只搜一个目录就下结论，以及引用过期二手快照，都是同一类错误。
3. **参照物不可信时宁可说测不出来**——假准确率比没有结论更有害，会让接手的人照着错数字排工期、跳过质检。

## 9. 方法论底线（写进每个结论里）

- 两版一致**只降低风险，不等于真值**；真值是字幕、原始文稿或人工复核。
- 同音**不能替代真值**；同源模型连置信度都要打折。
- 「两份文本差多少」是**差异度**，不是准确率；没有标准答案时不许换算成「提升 X%」。
- 二次转写的价值在**发现分歧**，不在**自动变准**。
- 一次性观察（单次计时、站点当期行为、下载速度）标注清楚，不作为硬结论。
- 推测写「很可能 / 属推断」，别用既成事实的语气。
- **一次只改一个变量**：参数对照要拆开跑，组合改动即使有效也不知道是谁起作用；「关提示语」和「开防胡说阈值」是两件事，别混在一次实验里。
- 会变的事实附「核实日期 + 复核命令 + 一手来源」。
- 结论要写**适用范围**：短口播、中英混读、长会议、朗读，彼此不能外推。

## 10. 还没解决的 / 下一步

1. **补一份标准答案**：哪怕只有 1 分钟人工听写稿，或一张术语表，才能把「谁更准」从定性变成定量。
2. **补标点 / 数字规整后处理**：让无标点但内容可用的引擎也能直接出稿，比换模型便宜。
3. **难样本复测**：开头试麦、多人抢话、长静音的素材，专门验证开头幻觉；干净样本测不出这类防护的效果。
4. **长音频验证**：≥5 分钟的素材单独测，别把短素材的速度结论外推。
5. **资源更空闲时再评估 torch 系方案**：先确认异源确有收益，再考虑引入重依赖。
6. **把「转完必做三查」（开头 / 结尾 / 中间长间隙）固化成流程步骤**，不靠人记（见 §0）。
7. **长间隙的便宜修法**：出现中间漏段时，先试 `vad_filter=False` 或调整 `min_silence_duration_ms` 重跑该片段，看能否恢复被切掉的内容——比换模型便宜；记录是否恢复，别默认「换引擎才能修」。
